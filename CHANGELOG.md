The table lists all **15** motors with the bus ID of each, the joint it drives, the physical bus it sits on, and whether a published policy drives it. / 新增 [`hardware/motor_ids.csv`](hardware/motor_ids.csv) 与 [`motor_ids.json`](hardware/motor_ids.json)、[`motor_ids.md`](hardware/motor_ids.md)、[`motor_ids.zh-CN.md`](hardware/motor_ids.zh-CN.md)，以及位置图 [`assets/wamoduck-motor-ids.png`](assets/wamoduck-motor-ids.png)。表中列出全部 **15** 个电机：各自的总线 ID、驱动的关节、所在的物理总线、以及是否由公开策略驱动。
- **This is hardware and interface information, not a performance claim.** Nothing on these pages says that a policy stands or walks, in simulation or on the robot; there is still no hardware result anywhere in this repository. / **这是硬件与接口信息，不是性能声称。** 这些页面没有一句说策略能站或能走 —— 无论是仿真还是实机；本仓库依然没有任何实机结果。
- The bus IDs come from the maintainer's own workbook `List_MotorID_CANFD.xlsx`, sheet `Sheet1`, **15** data rows, and every one of the **15** joint names was checked one by one against [`models/wmduck/wmduck.urdf`](models/wmduck/wmduck.urdf). The URDF and the MJCF both spell it `right_hip_yaw`, and the `note` field of the CSV keeps the original spelling on the record. / 有一处更正是**记录在案**而不是悄悄改掉的：源表把总线 2 上的关节拼作 `Rightt_hip_yaw`，属拼写笔误。URDF 与 MJCF 都拼作 `right_hip_yaw`，CSV 的 `note` 字段保留了原始拼写。
- **The three physical buses are recorded as the maintainer stated them on 2026-09-16.** The **AT32** main control board runs **three** CAN-FD buses on **XT30(2+2)** connectors, and those connectors carry power and CAN-FD together: one bus for the **left leg**, one for the **right leg**, and one for the **neck and head**. Each carries **5** motors, so **3 × 5 = 15**, which is exactly the **15** rows of the source table — the bus split and the table agree. / **三路物理总线按维护者 2026-09-16 的说明记录。** **AT32** 主控板走**三路** CAN-FD 总线，均用 **XT30(2+2)** 端子，该端子把电源与 CAN-FD 一起承载：**左下肢**一路、**右下肢**一路、**脖子及头部**一路。每路挂 **5** 个电机，即 **3 × 5 = 15**，恰好等于源表的 **15** 行 —— 总线划分与源表完全吻合。
- **The IDs on a single bus are not consecutive, and the page says so in the open.** The left-leg bus carries **1, 3, 5, 7, 9**; the right-leg bus carries **2, 4, 6, 8, 10**; the neck-and-head bus carries **11, 12, 13, 14, 15**. A left-leg bus does **not** use 1, 2, 3, 4, 5. / **单条总线上的 ID 不是连号，页面把这一点明写在最前面。** 左下肢总线是 **1、3、5、7、9**，右下肢是 **2、4、6、8、10**，脖子及头部是 **11、12、13、14、15**。左下肢总线**不**用 1、2、3、4、5。
- **Two orders that are not the same are written out side by side.** The bus ID order (**1, 2, 3 ... 15**, left/right interleaved) is the order of the `<actuator>` block in [`robot_walk.xml`](models/wmduck/mjcf/robot_walk.xml), the MJCF the policies were trained in. The **14**-dimension action vector, however, is read as **joint-tree order** (left leg 5, right leg 5, neck and head 4), so firmware and any host program have to permute once: `bus_id(action_index) = [1, 3, 5, 7, 9, 2, 4, 6, 8, 10, 11, 12, 13, 14]` for action index **0** to **13**. / **把两种并不相同的顺序并排写明。** 总线 ID 顺序（**1、2、3 …… 15**，左右交错）就是这些策略训练时所用 MJCF [`robot_walk.xml`](models/wmduck/mjcf/robot_walk.xml) 里 `<actuator>` 块的顺序；而 **14** 维动作向量是按**关节树顺序**解读的（左腿 5、右腿 5、颈头 4），因此固件与任何上位机程序都必须做一次置换：动作下标 **0** 到 **13** 对应 `bus_id(action_index) = [1, 3, 5, 7, 9, 2, 4, 6, 8, 10, 11, 12, 13, 14]`。
- **`mouth` is separated from the rest explicitly.** The published policies output **14** values, not **15**, because they have no beak axis. `mouth` is bus ID **15** and a real revolute joint in the URDF, but it is not in the action vector: `driven_by_policy` is `false` for it and its `action_index` is empty. / **`mouth` 被显式区分出来。** 公开策略输出的是 **14** 个值而不是 **15** 个，因为它们没有嘴部这一轴。`mouth` 的总线 ID 是 **15**、在 URDF 里也是真实的转动关节，但它不在动作向量里：它的 `driven_by_policy` 为 `false`、`action_index` 为空。
- **A prominent power-on warning sits on both pages.** The permutation has **not** been verified on a physical robot, so nothing should be energised on the strength of it; a wrong joint order mis-drives a joint and, in this project's own simulation, collapses the robot within a second. It is also **not settled**: an internal deployment-contract file reads the action vector in **actuator order**, and this repository's ROS 2 module [`model_contract.py`](ros2/wamoduck_ros2/wamoduck_ros2/model_contract.py) does the same, so under that reading `action[1]` targets bus ID **2** where this page sends it to bus ID **3** — the disagreement is unresolved. The bus direction and polarity, the termination resistors, and the ID assignment as actually programmed into the servos are unverified on hardware in the same way. / **两份页面都带一条醒目的上电警告。** 该置换**尚未**在实机上验证，因此不应据此给任何东西上电；关节顺序接错会错误驱动关节，而在本项目自己的仿真里，顺序接错会让机器人在一秒内瘫倒。它同样**尚未裁决**：一处内部部署契约文件按**执行器顺序**读动作向量，本仓库的 ROS 2 模块 [`model_contract.py`](ros2/wamoduck_ros2/wamoduck_ros2/model_contract.py) 也是同样读法，按那种读法 `action[1]` 的目标是总线 ID **2**，而本页把它发往总线 ID **3** —— 这个分歧尚未裁决。每一路总线的方向与极性、终端电阻、以及舵机里实际烧录的 ID 分配，也同样未在实机上验证。
- The drawing is an **export of the deck's only slide**, produced with Microsoft PowerPoint at **2400 × 1350** pixels and published unmodified. The deck contains **two** embedded CAD renders and no others, and those renders carry no bus IDs on their own: the numbers and the `Left` / `Right` labels are separate text shapes drawn over them, so an export is the only faithful form of the annotation. Neither the source workbook nor the source deck is redistributed here, so no `.xlsx` or `.pptx` enters this repository. / 位置图是**该幻灯片唯一一页的导出**，由 Microsoft PowerPoint 生成、尺寸 **2400 × 1350** 像素、原样公开。该幻灯片里只有**两张**内嵌 CAD 渲染图、没有别的图，而这两张图本身并不带总线 ID：数字与 `Left` / `Right` 标签是叠在其上的独立文本框，所以"把这一页导出"才是标注的唯一忠实形式。源工作簿与源幻灯片都不随本仓库分发，因此本仓库不会引入任何 `.xlsx` 或 `.pptx`。

### 2026-09-16 — Why the beak exists: planned uses, and what the model has today / 嘴部为什么存在：计划用途，以及模型今天的实际情况

- Added a **planned, not implemented** section to [`docs/roadmap.md`](docs/roadmap.md), plus one row in that page's deliverables table, explaining why bus ID **15** exists at all. This repository keeps a single bilingual [`docs/roadmap.md`](docs/roadmap.md) rather than a `roadmap.md` plus `roadmap.zh-CN.md` pair, so the new section is bilingual inside that file, sentence by sentence, the way the rest of the page is. / 在 [`docs/roadmap.md`](docs/roadmap.md) 里新增一节**计划中、未实现**的内容，并在该页交付表里加了一行，说明总线 ID **15** 到底为什么存在。本仓库的路线图是**单份双语** [`docs/roadmap.md`](docs/roadmap.md)，没有 `roadmap.md` 与 `roadmap.zh-CN.md` 这样一对文件，因此新增内容在同一文件内逐句双语，与该页其余部分一致。
- **Why it exists.** The beak is not in the **14**-dimension action vector any published policy outputs: it is a spare independent degree of freedom held back for human-robot interaction, and that is what explains the difference between **15** motors on the bus and **14** action values. / **它为什么存在。** 嘴部不在任何公开策略输出的 **14** 维动作向量里：它是一个被留给人机交互的备用独立自由度，这也正是"总线上 **15** 个电机、动作只有 **14** 个值"这一差异的原因。
- **Planned use 1 — sound feedback.** Close and open the beak in response to a human voice, with a module carrying speech recognition to be added later. / **计划用途 1 —— 声音反馈。** 听到人声后做张合嘴的反馈，后续会接一个带语音识别功能的模块。
- **Planned use 2 — holding a small ball.** Grip and hold a small ball in the cavity of the mouth, together with the on-board binocular structured-light depth camera. / **计划用途 2 —— 含住小球。** 用嘴里的空腔夹住并含住小球，结合机上的双目结构光深度相机。
- **The status is written as "planned, not implemented", in those words, and no date is promised.** The section also states what the model actually contains today, so that "planned" cannot be read as "supported". / **状态按"计划中，未实现"这几个字写明，也没有承诺任何日期。** 该节同时写出模型今天的实际情况，以免"计划中"被读成"已支持"。
- `mouth` is **one** revolute joint — parent `head_roll_link`, axis `0 1 0`, range **0** to **102.5** degrees in [`joint_limits.csv`](models/wmduck/joint_limits.csv) — so the mechanism is a bite plus a cavity hold, not a pinch. / `mouth` 是**单个**转动关节 —— 父 link 为 `head_roll_link`、轴向 `0 1 0`、在 [`joint_limits.csv`](models/wmduck/joint_limits.csv) 里范围是 **0** 到 **102.5** 度 —— 因此机制是"咬合 + 靠空腔含住"，不是捏取。
- **The simulation the policies are trained and published in has no cavity in the mouth.** In [`robot_walk.xml`](models/wmduck/mjcf/robot_walk.xml) — standing, sit/stand, walking, rough terrain — the **entire head chain has no collision geometry at all**. In [`robot_groundcontact.xml`](models/wmduck/mjcf/robot_groundcontact.xml) — get-up — the mouth is **one solid box**, `size="0.051375 0.041883 0.016277"`, and a MuJoCo box `size` is a half-extent, so that box is about **0.103 × 0.084 × 0.033** m with no cavity in it. The URDF is the opposite: `mouth_link`'s collision is the `Mouth.stl` mesh itself, so the CAD cavity is retained there. Simulating "holding a ball" therefore has to be built separately, with a collision representation of the cavity, a free ball body, and friction and contact tuning, and with the stability of concave-body and mesh contact verified on its own. / **公开策略训练与运行所用的仿真里，嘴里没有空腔。** 在 [`robot_walk.xml`](models/wmduck/mjcf/robot_walk.xml)（站立、坐站、行走、越障）里**整个头链没有任何碰撞体**；在 [`robot_groundcontact.xml`](models/wmduck/mjcf/robot_groundcontact.xml)（起身）里，嘴是**一个实心盒** `size="0.051375 0.041883 0.016277"`，而 MuJoCo 盒体的 `size` 是半边长，因此该盒约 **0.103 × 0.084 × 0.033** m、内部没有空腔。URDF 恰好相反：`mouth_link` 的碰撞体**就是 `Mouth.stl` 网格本身**，CAD 空腔在那里保留了。因此"含住球"的仿真必须另做：要给空腔一个碰撞表示、加一个自由小球刚体、调摩擦与接触参数，并单独验证凹体与网格接触的稳定性。
- **No model contains a camera, and the repository makes no perception claim.** `camera`, `depth`, and `stereo` appear nowhere in the URDF or in either MJCF, so the depth-camera plan has no representation in the simulation or in a perception chain yet; it is a new subsystem. / **模型里没有任何相机，本仓库也没有做感知声称。** `camera`、`depth`、`stereo` 在 URDF 与两个 MJCF 里都不出现，因此深度相机方案目前在仿真与感知链路里都没有表示，属于新子系统。
- **Holding a ball is a question of geometry and friction, not of torque.** The beak uses the same motor as the other **14**: **15** instances of the same HTDW3532 specification, rated **0.6** N·m. / **含球的成败取决于几何与摩擦，不是扭矩。** 嘴部电机与其余 **14** 个相同：**15** 个实例同为 HTDW3532、额定 **0.6** N·m。
- Wired the two pages together rather than leaving the beak plan in one place: the `mouth` row of [`hardware/motor_ids.csv`](hardware/motor_ids.csv) and [`motor_ids.json`](hardware/motor_ids.json) now say that bus ID **15** is reserved for interaction features and point at the roadmap, the closing bullet of both bus ID guides says the same in prose, and the roadmap links back to both guides. / 把两处内容互相接通，而不是让嘴部计划只待在一个地方：[`hardware/motor_ids.csv`](hardware/motor_ids.csv) 与 [`motor_ids.json`](hardware/motor_ids.json) 里 `mouth` 那一行现在写明总线 ID **15** 预留给交互功能并指向路线图，两份总线 ID 说明的对应条目也用文字写了同一件事，而路线图反过来链回这两份说明。
- Scope is unchanged: **planned work is not a result.** Nothing in this entry was implemented, nothing was measured, and there is still no hardware result anywhere in this repository. / 口径不变：**计划不是成果。** 本条没有任何内容被实现、也没有任何测量，本仓库依然没有任何实机结果。

### 2026-09-16 — Two reported `sitstand` problems, measured / 用户报告的 `sitstand` 两个问题，已实测

- A user playing the published demo reported two problems with the sit/stand policy, in their own words: with `sitstand` selected the duck **buzzes in place while standing**, and sitting down does not give "the head and torso vertical to the ground with the two legs braced symmetrically". Both were then measured — the report is quoted as the user gave it, and every number below is our own measurement taken afterwards. / 一位用户在实际玩公开 demo 时报告了坐／站策略的两个问题，原话是：切到 `sitstand` 后**鸭子站立时会原地抖动**，坐下也不是"头和躯干直立于地面、左右两腿对称对撑"的坐姿。两条随后都做了实测 —— 报告按用户原话引用，下面每个数字都是我们事后自己测的。
- The measurement used this repository's own published single-file runner, **CPU only**, MuJoCo **3.10.0** / ONNX Runtime **1.30.0** / NumPy **2.5.3**, 500 control steps (**10.0 s**) per run, spawn `nominal`, flat floor — `python wamoduck_sim.py --policy sitstand --target-height 0.175 --headless --steps 500`, the same command at `0.085`, and `python wamoduck_sim.py --policy stand --headless --steps 500` as the control. The per-step traces were recorded with a temporary harness outside the repository that drives `wamoduck_sim.Demo` and the same observe → act → apply → step loop the headless mode uses, so the run is the documented one and not a second implementation. / 测量用的是本仓库公开的单文件运行器，**纯 CPU**，MuJoCo **3.10.0**／ONNX Runtime **1.30.0**／NumPy **2.5.3**，每次运行 500 个控制步（**10.0 s**），出生点 `nominal`，平地 —— 命令为 `python wamoduck_sim.py --policy sitstand --target-height 0.175 --headless --steps 500`、把高度换成 `0.085` 的同一条命令、以及作为对照的 `python wamoduck_sim.py --policy stand --headless --steps 500`。逐控制步的轨迹由仓库外的一个临时测量脚本记录，它驱动的是 `wamoduck_sim.Demo` 与无界面模式同一条 observe → act → apply → step 循环，所以这是文档里写的那一次运行，不是第二套实现。
- **The two figures already on record reproduce.** The run holds **0.094 m** against a 0.085 m command and leans **~26°**, matching the numbers this repository already published for that command. What is new is the jitter and the left/right symmetry. / **已有记录的两个数字被重现了。** 这次运行在指令 0.085 m 时维持 **0.094 m**、倾斜约 **26°**，与本仓库此前公布的该指令数字一致。新测到的是**抖动**与**左右对称性**。
- **Problem 1 — the standing posture buzzes in place.** At a 0.175 m command the robot is upright (final tilt **0.44°**, base height **0.1762 m**) and never settles: action jitter, `mean abs(delta a)` per control step — the same metric row 1 of the capability board uses — is **0.229** over the whole 10 s, **0.235** after the first 1.0 s and **0.236** in the last 1.0 s, with a maximum single step of **1.313**; tilt std **0.403°** (**0.396°** in the last second, so it is a sustained limit cycle rather than a settling transient); base-height std **1.10 mm**; mean absolute joint velocity **1.69 rad/s** with a peak of **10.11 rad/s**. The `stand` policy on the same metric and the same run length gives **9.9e-5**, **2.9e-7** and **4.1e-8**, i.e. about **six orders of magnitude** quieter, so this is a property of the sit/stand policy and not of the runner. Both soles are down in only **92.2 %** of the steps after the first second and the feet carry **45.46 N** on average against a **36.80 N** weight — the buzz is pushing the ground — and "in place" is approximate, because it also travels **0.263 m** over the 10 s. / **问题一 —— 站立姿态原地抖动。** 0.175 m 指令下机器人是直立的（末态倾角 **0.44°**、基座高度 **0.1762 m**），但**始终不收敛**：动作抖动（每控制步的 `mean abs(delta a)`，正是能力清单第 1 行所用的那个指标）整 10 s 为 **0.229**、去掉前 1.0 s 为 **0.235**、末 1.0 s 为 **0.236**，单步最大 **1.313**；倾角标准差 **0.403°**（末 1 s 为 **0.396°**，所以这是持续的极限环而不是会衰减的过渡过程）；基座高度标准差 **1.10 mm**；关节速度绝对值均值 **1.69 rad/s**、峰值 **10.11 rad/s**。同一个指标、同样运行长度下 `stand` 策略是 **9.9e-5**、**2.9e-7**、**4.1e-8**，安静约**六个数量级**，所以这是坐／站策略本身的性质、不是运行器的性质。去掉前 1 s 后只有 **92.2 %** 的步数双脚同时着地，双脚平均承担 **45.46 N** 而整机重量是 **36.80 N** —— 抖动的力是蹬在地面上的 —— 而"原地"也只是近似：10 s 里它同时还挪了 **0.263 m**。
- **Problem 2 — the sitting posture is neither upright nor left/right symmetric.** At a 0.085 m command the pose is **quiet** (it reaches a static pose inside about 1 s: `mean abs(delta a)` **4.4e-7** and tilt std **1.3e-4°** in the last second), so the jitter is a standing-height problem only; pressing `m` mid-run lands on the same pose. But that quiet pose is a **25.89°** lean (roll **−15.99°**, pitch **+20.64°**) held at **0.0943 m** instead of the commanded 0.085 m (**+9.3 mm**), with the head — `head_roll_link` — **25.62°** off vertical and the neck **25.44°** off, because the head chain's own joints are all within **0.6°** of zero and simply inherit the trunk's lean.
